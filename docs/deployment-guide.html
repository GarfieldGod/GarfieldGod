GarfieldGod 站点部署
与后台访问控制指南

后台入口采用独立路径 garfieldgod.cn/admin，由 Cloudflare Access 在边缘完成身份校验； 源站只接受经 Cloudflare 回源的请求，应用侧通过 GG_TRUST_ACCESS=1 放行。 本文按顺序给出可照做的操作步骤。

站点：garfieldgod.cn 栈：Nuxt 3 + Nitro + node:sqlite 更新：2026-09-28
总览

请求链路

用户请求先到 Cloudflare，通过 Access 策略后才回源到你的服务器。

访问者浏览器 / 手机
→
Cloudflare 边缘DNS · SSL · Access 策略
→
源站 Nitro只接受 CF 回源
→
SQLite + 上传目录.data/ 持久化
为什么要让源站只接受 Cloudflare 回源

Cloudflare 会把请求头原样转发给源站，其中就包括 Access 注入的 CF-Access-Authenticated-User-Email。如果源站 IP 可以直接访问， 攻击者伪造这个请求头就能绕过整套鉴权。所以第 3 步（锁定源站）不是可选项。

访问控制模式与优先级

守卫按以下顺序判断，先命中先返回，因此接入 Access 后不要保留口令配置：

模式触发条件行为
password设置了 GG_ADMIN_PASSWORD口令换 8 小时会话 cookie；优先级最高
accessGG_TRUST_ACCESS=1要求携带 CF-Access-Authenticated-User-Email 头
devNODE_ENV !== production直接放行，仅用于本地开发
locked生产环境且上面都不满足返回 403 并提示配置方式，避免后台裸奔
最容易踩的坑

接入 Cloudflare Access 后，必须删掉 GG_ADMIN_PASSWORD。 只要它还在，守卫就停留在口令模式，Access 头会被忽略——你会通过 Cloudflare 校验后又被自己的登录页拦一次。

第一步

域名接入 Cloudflare

这一步在 Cloudflare 控制台与域名注册商完成。

  1. 添加站点 登录 Cloudflare，Add a site，输入 garfieldgod.cn，选择 Free 计划。
  2. 核对 DNS 记录 Cloudflare 会自动扫描现有记录。确认 A/AAAA 记录指向你的源站 IP， 且代理状态为 Proxied（橙色云）。若源站用 Tunnel，则改为 Tunnel 生成的 CNAME。
  3. 在注册商处修改 NS 把域名的 NS 改成 Cloudflare 分配的两个地址，等待生效（通常几分钟，最长 24 小时）。 生效后 dig NS garfieldgod.cn 应返回 Cloudflare 的域名服务器。
  4. 设置加密模式 SSL/TLS → Overview → 选择 Full (strict)。 源站需有有效证书（Cloudflare Origin Certificate 或 Let's Encrypt 均可）。
  5. 强制 HTTPS Edge Certificates → 打开 Always Use HTTPS 与 Automatic HTTPS Rewrites。
加密模式不要选 Flexible

Flexible 会让 Cloudflare 到源站走明文 HTTP，既无法保证 Full (strict)，也容易被中间人利用。

第二步

源站部署

把站点跑起来，并让数据落在持久化目录。

# 构建
npm ci
npm run build

# 运行（Node ≥ 22.5，内置 node:sqlite；本项目实测 22.16）
node .output/server/index.mjs

生产环境变量

NODE_ENV=production
GG_TRUST_ACCESS=1
# 持久化路径，建议放在用户目录或独立数据盘
GG_DB_PATH=/var/lib/garfieldgod/garfieldgod.db
GG_UPLOAD_DIR=/var/lib/garfieldgod/uploads
PORT=3000
生产环境不会自动读取 .env

Nuxt 只在 dev/build 阶段自动加载 .env。直接 node .output/server/index.mjs 时需用 systemd 的 EnvironmentFile，或 node --env-file=.env .output/server/index.mjs 注入。 完整变量清单见仓库根目录的 .env.example。

systemd 单元示例

[Unit]
Description=GarfieldGod site
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/srv/garfieldgod
EnvironmentFile=/srv/garfieldgod/.env
ExecStart=/usr/bin/node .output/server/index.mjs
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target

需要备份的两样东西

  • GG_DB_PATH 指向的 SQLite 文件（连同 -wal/-shm，或先停服务再拷贝）
  • GG_UPLOAD_DIR 上传目录
第三步

锁定源站

三选一，按可靠性排序。这一步决定了鉴权能否被绕过。

A. Cloudflare Tunnel（推荐）

源站完全不开放公网入站端口，由 cloudflared 主动向 Cloudflare 建立隧道。 源站 IP 不可达，伪造请求头无从谈起。 

# 源站上安装后登录授权
cloudflared tunnel login
cloudflared tunnel create garfieldgod
cloudflared tunnel route dns garfieldgod garfieldgod.cn

# config.yml
tunnel: garfieldgod
credentials-file: /root/.cloudflared/<tunnel-id>.json
ingress:
  - hostname: garfieldgod.cn
    service: http://127.0.0.1:3000
  - service: http_status:404

# 常驻
cloudflared service install

防火墙同时关闭 80/443 的公网入站，只保留 SSH。

B. 防火墙仅放行 Cloudflare 回源 IP

保留公网端口，但只允许 Cloudflare 的 IP 段访问。 注意 Cloudflare 会更新 IP 列表，需要定期同步（官方在 cloudflare.com/ips-v4 与 ips-v6 提供）。

C. Authenticated Origin Pulls（mTLS）

在 SSL/TLS → Origin Server 打开，源站校验 Cloudflare 客户端证书。 配置量比 A 大，且仍需保证源站不被直连绕过。

可选加固：共享密钥

若暂时无法做到 A/B/C，可再加一层：用 Transform Rule 给所有回源请求注入一个自定义头， 应用侧比对同值。本项目已支持，设 GG_ACCESS_SECRET 即启用。 

# Cloudflare 控制台：Rules → Transform Rules → Modify Request Header
# 规则：当 主机名 等于 garfieldgod.cn
# 操作：Set 静态值
x-gg-access-secret: <一串随机字符串>

# 源站 .env
GG_ACCESS_SECRET=<同一串随机字符串>

该头由 Cloudflare 覆盖写入，访问者无法自带。启用后即缺少该头的请求一律拒绝， 为源站被直连的情况兜底。生成随机值可用 openssl rand -hex 32。

第四步

配置 Cloudflare Access

在 Zero Trust 里为后台路径加一道身份校验。免费版支持 50 个用户。

  1. 进入 Access Cloudflare 控制台左侧 Zero Trust → Access → Applications， 点 Add an application，选择 Self-hosted。
  2. 创建后台页面应用 应用名 GarfieldGod Admin； Application domain 填 garfieldgod.cn，Path 填 admin。 Path 会自动覆盖 /admin 及其所有子路径。
    注意：Path 不要写前导斜杠。
  3. 再加一个后台接口应用 同样方式创建第二个应用，Path 填 api/admin。 页面和接口分开建，便于分别看日志与调策略。
  4. 写放行策略 在策略区：Action 选 Allow，Include 选 Emails，填入你自己的邮箱。 只有名单内的身份能通过。
  5. 开启二次验证 同页面的 Authentication 区域，把 Login methods 设为 One-time PIN（邮箱验证码） 或你已接入的身份源（Google / GitHub 等）。 需要更强保证时，在策略下加一条 Require → MFA。
  6. 设置会话时长 建议 24 小时。到期后需要重新验证一次，之后一段时间内不再打断。
  7. 保存并回到源站启用 确认源站 .env 为 GG_TRUST_ACCESS=1， 且没有 GG_ADMIN_PASSWORD，然后重启服务。
验证过的守卫行为

在 Access 模式下实测：不带任何头的 /api/admin/* 返回 401、页面 302 跳转； 只有伪造的 CF 头而没有共享密钥时返回 401；两个头都正确时返回 200。公开站不受影响。

第五步

验收清单

逐条确认，全部通过即可认为接入完成。

  • 无痕窗口访问 https://garfieldgod.cn/，首页正常，说明公开站未被 Access 拦住。
  • 无痕窗口访问 https://garfieldgod.cn/admin，先跳到 Cloudflare 登录页，验证邮箱后进入后台。
  • 未登录状态直接请求 https://garfieldgod.cn/api/admin/stats，返回 401 或跳转登录，不返回数据。
  • 后台能新建一篇文章、上传一张图片，并在公开页看到渲染结果。
  • 提交一条评论，在后台评论页能审核通过。
  • 直接访问源站 IP（如 http://<源站IP>:3000/admin）应连接失败或被拒绝。
  • 服务器重启后数据仍在，GG_DB_PATH 与上传目录指向的是持久化位置。
附录

排障与回滚

现象原因与处理
通过 Cloudflare 验证后又被自己的登录页拦住 设了 GG_ADMIN_PASSWORD，守卫停在口令模式。删掉它并重启。
生产环境访问后台返回 403「后台未启用访问控制」 既没有 GG_TRUST_ACCESS=1 也没有口令，属预期的安全兜底。按第四步配置。
Access 已放行，但接口仍返回 401 源站没收到 CF-Access-* 头。检查 Access 应用的 Path 是否写对、请求是否确实走了 Cloudflare。
上传图片后页面 404 GG_UPLOAD_DIR 目录不存在或不可写，检查运行用户权限。
上传报「文件超过 20MB 限制」 单文件上限 20MB，且仅允许 png/jpg/gif/webp/avif/mp4/webm/mp3。
想临时用口令进后台 设 GG_ADMIN_PASSWORD 即退回口令模式（会同时忽略 Access 头）。

回滚

  • 临时放开后台：删除两个 Access 应用即可恢复公开访问。
  • 退回口令模式：设置 GG_ADMIN_PASSWORD，无需改代码。
  • 域名迁回：在注册商处把 NS 改回原值。
